# v0.1 launch: cross-surface persona infrastructure

## Problem Statement

Matt Stone authors content in at least three distinct identities — Lithos Uplift (consulting), Northwest Hub (board), StoneGynOnc (family practice) — across at least three surfaces (Claude Code on the desktop, claude.ai web/desktop/mobile, Codex/opencode). Each identity has its own Voice (tone rules, anti-patterns, few-shot exemplars) and per-Channel content (email signature and contact block; future: slack format, board memo conventions). Today, identity-bearing content lives entangled with the executable skill (e.g. `/lithos-voice` mixes prompt mechanics with private voice rules), which means:

- Publishing the skill repo publicly would leak identity content.
- Adding a fourth persona requires duplicating the entire skill body, then editing.
- The same skill can't run on claude.ai without forking the implementation (claude.ai has no filesystem outside the uploaded bundle).
- The user's existing `/lithos-voice`, `/lithos-email` muscle memory has to either survive a refactor or be abandoned.

## Solution

Ship a **Tier 1 + Tier 2 split** with a documented Resolver chain that spans all three Surfaces:

- **Tier 1 Generic skills** live in this public repo (`skills/productivity/voice/`, `skills/productivity/email/`). They take a Persona slug as `$ARGUMENTS`, implement an inline 4-path Resolver chain, load the relevant Channel file from the resolved Persona directory, and apply it. They contain zero identity content.
- **Tier 2 Shims** live in a private dotfiles `stonematt-skills` stow package. Each Shim is a thin SKILL.md that declares persona-specific natural-language triggers (e.g. "write as nwhub", `/nwhub-voice`) and delegates to a Tier 1 Generic skill with the persona slug pre-bound. Optional — Tier 1 works without any Shim installed.
- **Persona content** lives at `$XDG_CONFIG_HOME/stonematt-skills/persona/<slug>/<channel>.md` (private; managed by the dotfiles stow package). The hybrid file shape — 5 to 15 bullet rules + 3 to 5 labeled Input/Output few-shot pairs + numeric targets + anti-patterns — is the schema; the content is the user's.
- **Cross-surface mechanism**: on Claude Code and Codex/opencode, the Resolver hits the XDG path or an env override. On claude.ai (no host filesystem), `scripts/build-claudeai-zip.sh <skill> <persona...>` copies selected `persona/<slug>/` directories into a zip alongside the Generic skill; once uploaded, the Resolver finds them under `$SKILL_DIR/persona/...` inside the bundle.
- **Bootstrap**: `bin/persona-init <slug>` scaffolds both sides (the persona-content templates AND the matching Tier 2 Shims) in one run.
- **Quality gate**: `ai-sniff-test` is wired as auto-invoke for long-form output from `voice` and `email`, with `--skip-sniff` opt-out for short-form / iteration cycles.

See [ADR-0001](../adr/0001-cross-surface-persona-architecture.md) for the architectural rationale and [CONTEXT.md](../../CONTEXT.md) for the canonical glossary (Skill, Bucket, Persona, Channel, Generic skill, Shim, Tier 1/2, Resolver, Surface, Bundle, Persona init).

## User Stories

1. As a multi-identity author, I want a single Generic skill `voice` that takes a Persona slug, so that I do not duplicate the skill body per identity.
2. As a multi-identity author, I want a single Generic skill `email` that takes a Persona slug, so that email-shaped output reuses the same Persona content alongside per-Channel additions (signature, contact block).
3. As an OSS publisher, I want all identity-bearing content out of the public repo, so that I can publish stonematt-skills without leaking private voice rules.
4. As a user with `/lithos-voice` muscle memory, I want a Tier 2 Shim that preserves my existing slash command and natural-language triggers, so that I do not retrain habits.
5. As a Claude Code user, I want the Resolver to honor an env override (`$STONEMATT_SKILLS_CONFIG`) ahead of XDG, so that I can point a session at an alternate persona directory for testing.
6. As a Claude Code user, I want the Resolver to fall back to XDG (`$XDG_CONFIG_HOME/stonematt-skills/persona/<slug>/<channel>.md`), so that my private dotfiles drive Persona content by default.
7. As a claude.ai web user, I want the Resolver to fall back to `$SKILL_DIR/persona/<slug>/<channel>.md` so that bundled Persona content inside the uploaded zip is findable.
8. As a developer iterating on a Persona, I want the Resolver to fall back to a relative `./persona/<slug>/<channel>.md` so that I can test against a fixture without touching XDG.
9. As a developer, I want the Resolver to return a clear error when no path hits, so that I know whether the failure is missing-content vs. misconfiguration.
10. As an author drafting long-form copy, I want `voice` and `email` to auto-pipe output through `ai-sniff-test`, so that AI tells get caught before I send.
11. As an author iterating on short-form output, I want `--skip-sniff` to bypass the gate, so that quick passes do not pay the gate cost.
12. As an author scaffolding a new Persona, I want `bin/persona-init <slug>` to write the XDG-side `voice.md` and `email.md` templates AND the dotfiles-side Tier 2 Shims in one run, so that adding a new identity is a single command.
13. As a Persona scaffolder, I want `bin/persona-init` to be idempotent (skip files that already exist), so that re-running it is safe.
14. As a Persona scaffolder, I want `bin/persona-init` to read `STONEMATT_DOTFILES_DIR` from env (prompting if unset), so that the script does not assume a fixed dotfiles location.
15. As a Persona scaffolder, I want the Persona templates to embed the hybrid shape (5-15 bullet rules + 3-5 few-shot pairs + numeric targets + anti-patterns), so that new Personas inherit a research-validated structure.
16. As a claude.ai user, I want `scripts/build-claudeai-zip.sh <skill> <persona...>` to produce an uploadable zip with the Generic skill and selected Persona content, so that I can run the skill on claude.ai web.
17. As a claude.ai user, I want the bundle layout to match what the Resolver expects under `$SKILL_DIR/persona/...`, so that the same Generic skill body works without surface-specific branching.
18. As a Lithos consultant, I want a `lithos` Persona scaffolded with `voice` and `email` channels, so that I can resume `/lithos-voice` and `/lithos-email` workflows on Claude Code.
19. As an NWHub board member, I want an `nwhub` Persona scaffolded with `voice` and `email` channels, so that board memos and board-related email share a voice.
20. As a StoneGynOnc stakeholder, I want a `stonegynonc` Persona scaffolded with `voice` and `email` channels, so that family-business comms have brand-aligned voice.
21. As a downstream consumer, I want a `v0.1.0` git tag once the above lands, so that I can pin against a known-good state via `npx skills add stonematt/stonematt-skills@v0.1.0`.
22. As a downstream consumer, I want the v0.1.0 release notes to summarize the Resolver chain, the Tier 2 Shim convention, and the bundle format, so that I know what to re-zip or reconfigure on upgrade.
23. As a developer reading the public repo, I want the README to show how to invoke Tier 1 explicitly with a persona arg, how to invoke a Tier 2 Shim, how to scaffold a new Persona, and how to build a claude.ai Bundle, so that onboarding does not require reading every ADR.
24. As an AFK agent picking up a slice, I want each issue body to stand alone (parent brief reference + acceptance criteria + scope notes), so that I do not have to read back to the brief to start work.

## Implementation Decisions

### Modules

- **Resolver** (deep module, replicated inline per Generic skill body)
  - Interface: `resolve_persona(slug, channel) → file path | error`
  - Body: ordered checks `$STONEMATT_SKILLS_CONFIG/persona/<slug>/<channel>.md` → `${XDG_CONFIG_HOME:-$HOME/.config}/stonematt-skills/persona/<slug>/<channel>.md` → `$SKILL_DIR/persona/<slug>/<channel>.md` → `./persona/<slug>/<channel>.md`. First-hit wins. No-hit returns an error citing all four attempted paths.
  - Per ADR-0001 consequence: replicated inline per Generic skill, not extracted to a shared library, so that each skill is self-contained on claude.ai (no source-relative imports inside a zip bundle).
  - Tested per skill via fixture under `./persona/test/`.

- **Generic `voice` skill** (`skills/productivity/voice/SKILL.md`)
  - Args: `--persona <slug>` (required), `--skip-sniff` (optional)
  - Triggers: intent-based ("write in my voice", "review for voice") + explicit `/voice`
  - Body: parses args, invokes Resolver for `voice` channel, loads file, applies as voice-rules system message for drafting OR as voice-rules rubric for review. Long-form output auto-piped through `ai-sniff-test` unless `--skip-sniff`.

- **Generic `email` skill** (`skills/productivity/email/SKILL.md`)
  - Args: `--persona <slug>` (required), `--skip-sniff` (optional), plus email-shape args (recipient, subject, register) as needed
  - Triggers: intent-based ("draft email as <persona>", "reply as <persona>") + explicit `/email`
  - Body: parses args, invokes Resolver for `email` channel AND `voice` channel, loads both, composes email-shape output (signature + contact from `email.md`, voice rules from `voice.md`). Long-form auto-piped through `ai-sniff-test`.

- **Persona file schema** (contract, not code)
  - Hybrid shape per ADR-0001 research: 5-15 bullet rules + 3-5 labeled Input/Output few-shot pairs + numeric targets (sentence length, paragraph count, etc.) + explicit anti-patterns ("never start with 'I just wanted to...'"). Plain markdown, no frontmatter required.
  - Per-Channel files: `voice.md`, `email.md` (this initiative). `slack.md`, `board-memo.md` deferred.

- **`bin/persona-init <slug>`** (deep module, single-binary scaffolder)
  - Interface: `persona-init <slug> [--dry-run]`
  - Inputs: `STONEMATT_DOTFILES_DIR` env (prompted if unset); `XDG_CONFIG_HOME` (defaults to `$HOME/.config`)
  - Outputs: writes hybrid-shape templates to `$XDG_CONFIG_HOME/stonematt-skills/persona/<slug>/{voice,email}.md` AND Tier 2 Shims to `$STONEMATT_DOTFILES_DIR/stonematt-skills/dot-claude/skills/<slug>-{voice,email}/SKILL.md`
  - Idempotent (skip-existing per file). `--dry-run` prints planned writes without touching disk.

- **`scripts/build-claudeai-zip.sh`** (already scaffolded, needs validation)
  - Interface: `build-claudeai-zip.sh <skill> <persona-slug...>`
  - Output: `dist/<skill>-<slugs>.zip` containing `SKILL.md` + `persona/<slug>/*.md` for each requested persona, laid out so the Resolver's `$SKILL_DIR/persona/...` branch hits.

- **Tier 2 Shim convention** (template, not code)
  - SKILL.md body: 5-15 lines. Frontmatter declares persona-specific triggers (e.g. `/lithos-voice`, "write as lithos"). Body invokes Tier 1 generic with `--persona <slug>` pre-bound. No identity content in the Shim — that lives in the resolved Persona file.

### Architectural decisions (already locked by ADR-0001)

- Resolver chain: env → XDG → `$SKILL_DIR` → cwd. First-hit wins.
- Cross-surface bundle: claude.ai zip carries persona content inline; Resolver path `$SKILL_DIR/persona/...` is the bundle branch.
- Tier 1 holds executable; Tier 2 holds triggers + delegation. Tier 1 is sufficient on its own; Tier 2 is ergonomic sugar.
- `ai-sniff-test` is the long-form quality gate, auto-invoked.

### API / interface contracts

- All Generic skills accept `--persona <slug>` as the canonical persona selector.
- All Generic skills accept `--skip-sniff` to bypass the quality gate.
- Resolver error format: cite all 4 paths attempted, plus the slug+channel that failed, so the user can debug.
- Tier 2 Shims pre-bind `--persona`; users invoke shims without arguments for the common case.

### Out of repo (lives in private dotfiles)

- Actual Persona content for `lithos`, `nwhub`, `stonegynonc`.
- Tier 2 Shim instances (`lithos-voice`, `lithos-email`, `nwhub-voice`, `nwhub-email`, `stonegynonc-voice`, `stonegynonc-email`).
- These ship via the user's dotfiles `stonematt-skills` stow package. This brief tracks the scaffolding output of `bin/persona-init` but not the hand-authored voice content.

## Testing Decisions

Good tests in this codebase verify externally observable behavior: "does the Resolver return the correct path under these env conditions?" not "does the Resolver call `realpath` internally?" Tests use fixture personas under `./persona/test/` rather than mocking the filesystem.

### Modules to test

- **Resolver, per Generic skill** — fixture tests covering each of the 4 paths (env override, XDG default, `$SKILL_DIR` bundle, cwd relative), first-hit-wins behavior, and the no-hit error case. Tests live alongside the skill under `skills/productivity/<skill>/test/`.
- **`bin/persona-init`** — black-box test: given a temp `XDG_CONFIG_HOME` and `STONEMATT_DOTFILES_DIR`, runs `persona-init test`; asserts files exist with hybrid-shape headers, asserts re-run is no-op, asserts `--dry-run` writes nothing.
- **`scripts/build-claudeai-zip.sh`** — black-box test: given a test persona under `./persona/test/`, runs the builder; asserts the resulting zip contains `SKILL.md` + `persona/test/*.md` at the expected layout. Smoke test on real claude.ai upload happens out-of-band (HITL slice).

### Prior art

No tests exist in this repo yet — this initiative establishes the test pattern. Closest external reference: skill-test patterns from `mattpocock/skills` use bash-driven black-box fixtures, which this repo will follow (Bash + grep on output, no test framework).

## Out of Scope

- Persona content authoring for `lithos`, `nwhub`, `stonegynonc`. User authors these in the private dotfiles; this brief scaffolds templates, not content.
- Channels beyond `voice` and `email`. `slack`, `board-memo`, etc. are deferred.
- Migrating `~/.claude/hooks/` and `vault-operator` — separate concerns in separate repos.
- Hook/agent/command integration into `plugin.json` — schema does not support; defer.
- Skill-by-skill git history preservation from prior dotfiles location — possible via `git format-patch` for ~5 author-original commits; defer unless requested.
- claude.ai-specific tooling beyond the bundle builder (e.g. auto-upload via API). Manual upload is the v0.1 workflow.

## Further Notes

- **Sequencing**: tracer slice (issue #4) covers `voice` Generic skill + `nwhub` Persona end-to-end across both Surfaces, deliberately constrained to one Channel and one Persona to validate every layer once before fanning out. Follow-up slices (`email` Generic, `lithos` and `stonegynonc` Personas, `persona-init` multi-channel, `v0.1.0` tag) inherit whatever patterns the tracer establishes.
- **HITL vs AFK boundary**: claude.ai upload step is HITL (user must upload to web and confirm). All other slices in this initiative should be AFK-scopeable.
- **Public/private boundary**: every artifact in this initiative is either fully public (Generic skill bodies, Resolver chain, bundle builder, Persona init scaffolder, hybrid-shape templates) OR fully private (Persona content, Tier 2 Shim instances). The boundary is the file, not the line. No identity fingerprints in the public repo.
- **Prior art uniqueness**: the cross-surface Resolver pattern (CC filesystem + claude.ai zip-bundle path resolution) is not published elsewhere as of 2026-05-13. Closest analogs documented in handoff. Tracer outcome may inform whether this pattern is worth a write-up for the wider community.
